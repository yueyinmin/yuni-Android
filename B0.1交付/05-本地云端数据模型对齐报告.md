## 1. 实际检查内容

审计发现 4 个结构缺口 + 2 个逻辑缺口：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | `diary` 没有 `coupleId` | 共享日记不知道属于哪个空间，跨空间数据会串 |
| 2 | `daily_question` 没有 `coupleId` / 同步字段 | 两个空间同一天撞唯一键；无法参与增量同步 |
| 3 | `letter` 没有草稿正文 / 状态 / 空间 | 写信中途退出会丢草稿；草稿会被误当成未解锁的信 |
| 4 | 没有 `message` 表 | B6「悄悄话」无处可存 |
| 5 | Outbox 的 `insertOrReplace` 每次用新 UUID | 覆盖不了旧任务，同一改动会重复上传 |
| 6 | Outbox 只挡 PRIVATE，没挡「SHARED 但没空间」 | 历史数据上云只会被 RLS 拒绝，白耗请求 |

## 3. 修改前后差异（表结构）

| 表 | v1 | v2 |
|---|---|---|
| diary | 11 列 | + `coupleId TEXT`（可空） |
| daily_question | 8 列，唯一索引 `(questionEpochDay)` | + `coupleId`、`updatedAt`(默认0)、`syncStatus`(默认 LOCAL_ONLY)、`serverVersion`(默认0)；唯一索引改 `(coupleId, questionEpochDay)` |
| letter | 8 列 | + `coupleId`、`localDraftContent TEXT`、`status TEXT NOT NULL DEFAULT 'DRAFT'` |
| message | 不存在 | 新建，13 列 + 4 个索引 |
| 其余 8 张表 | 不变 | 不变 |

### 迁移里的三条硬规矩

1. **不给历史数据编造 coupleId。** 迁移里所有新加的 `coupleId` 都是 NULL。历史数据都是"绑定空间之前写的"，没人知道它属于哪个空间。猜一个等于把数据挂到别人空间下，比留空危险得多。NULL 的语义是"待认领"。
2. **`updatedAt` 用 `createdAt` 回填。** 增量同步靠 `server_updated_at > 游标`，历史行留在 0 永远拉不到。
3. **ALTER 加 NOT NULL 列必须有 DEFAULT**（SQLite 强制）；新建 message 表则不需要 DEFAULT。

## 4. 安全边界落在代码里的位置

| 边界 | 实现 |
|---|---|
| 未揭晓的对方答案不进内存 | `DailyQuestionDao.observeAll()` / `byDay()` 的 SQL：`CASE WHEN revealed = 1 THEN partnerAnswer ELSE NULL END` |
| 私密日记不入队 | `OutboxWriter.enqueueDiary` 第 1 道闸门 + `DiaryRepositoryImpl.add/update` 的 `syncable` |
| 没有空间的共享日记不入队 | `OutboxWriter.enqueueDiary` 第 2 道闸门 + `DiaryDao.pendingUploadShared` 的 `coupleId IS NOT NULL` |
| 草稿正文永不上云 | `LetterEntity.localDraftContent` 不出现在任何 Outbox payload；入队函数没有该字段 |
| 更新时不能搬空间 | `DiaryRepositoryImpl.update` 使用 `existing.coupleId`，忽略传入值 |
| 消息入队也要有空间 | `MessageDao.pendingUpload` 带 `coupleId IS NOT NULL` |

### MigrationTest 覆盖的 8 件事
1. v1 → v2 历史数据一条不丢（日记 2 条、问答 1 条、信 1 条，内容比对）。
2. 不给历史数据编造 `coupleId`（三张表全为 NULL）。
3. `updatedAt` 用 `createdAt` 回填，不是 0。
4. letter 新列默认 DRAFT、草稿正文为 NULL。
5. message 表能写入读出，`receiverId` 允许 NULL。
6. message 的 4 个索引都在。
7. 问答唯一索引改成复合：两个空间同一天各一条可以共存，同空间同一天第二条被拒。
8. `user_version` 推进到 2。

### 为什么不用 Room 官方 MigrationTestHelper
它要求 schema json 在 assets 里。实测 AGP 8.7 **不会**把 `sourceSets.test.assets` 合并进单测资源（`generateDebugUnitTestAssets` 后没有任何 json）。把 schema 塞进 main assets 等于让生产 APK 背上数据库结构文件，不值。所以自己实现 helper 内核：读 `1.json` 的 `createSql` 建真 v1 库（含 `room_master_table` 和 v1 identityHash）→ 用 Room(v2) 打开 → **由 Room 自己做 `validateMigration`**。schema 正确性由 Room 判定，测试只断言数据有没有丢。

### 过程中真实踩的坑（留痕）
- 第一次：Robolectric 实例化真实 `YuniApplication`，`onCreate` 调 WorkManager 抛 `IllegalStateException` → 改 `@Config(application = android.app.Application::class)`。
- 第二次：`FileNotFoundException: Missing file .../1.json` → 改为自建 v1 库。
- 第三次：`NOT NULL constraint failed: daily_question.revealed`（v1 该列没有 DEFAULT）→ INSERT 显式给 `revealed = 0`。

## 6. 尚未解决的问题
- **`fallbackToDestructiveMigration()` 没有使用**，这是对的；但 v1 老用户真正升级的现场验证还没做（本机没有装过 v1 版 APK 的真机）。迁移测试是 Robolectric 上的真 SQLite，不是真机升级。
- 历史 `coupleId = NULL` 的数据"如何认领"是产品决策：B1 绑定空间时需要给出明确规则（提示用户重新归类 / 保持仅本机 / 其他）。**待决策**，本轮不替用户决定。

- `letter` 的正式正文仍不在本地表（设计如此，属 B6）。
