# 一、项目概述

## 1.1 项目背景

「予你 · Us」是一款面向两个人的私密关系陪伴应用。

它不是传统的社交软件，也不是简单的纪念日倒计时工具，更不是要求双方每天完成任务的打卡应用。

它希望成为两个人共同拥有的一处数字空间。

在这里，两个人可以记录共同经历、保存照片、写下日记、回答每日问题、交换悄悄话、给未来的彼此写信，也可以记录下一次见面计划和共同愿望。

对于异地恋用户而言，它还承担着连接两个人日常生活的作用，让无法时刻见面的人，也能持续感受到彼此的存在。

## 1.2 产品核心理念

产品名称：予你 · Us

核心表达：

**把日子交给时间，把回忆留给彼此。**

产品希望传递三种体验：

1. 陪伴：即使不在同一个地方，也能感受到对方参与自己的生活。
2. 记录：把普通日子变成值得回看的共同记忆。
3. 期待：让纪念日、未来的信件和下一次见面成为两个人共同期待的事情。

## 1.3 产品定位

定位为：

**一个由两个人共同拥有、以共同回忆为核心、以轻量互动为纽带的私密数字空间。**

产品不以用户增长、社交传播、商业化和复杂社区功能为目标。

初期只服务两个人，不考虑公开动态广场、陌生人匹配、公开评论区和内容推荐算法。

## 1.4 产品设计原则

| 原则 | 具体要求 |
|---|---|
| 私密性 | 默认只有绑定的两个人可以访问共同空间 |
| 自愿性 | 不强制打卡，不制造未完成任务的压力 |
| 本地优先 | 没有网络也可以记录和查看本地数据 |
| 双人互动 | 重要互动应当体现双方参与 |
| 温暖简洁 | 视觉上有陪伴感，但不堆砌装饰 |
| 数据安全 | 个人私密内容与共同内容严格隔离 |
| 免费优先 | 当前所有开发和运行方案以 0 元为目标 |
| 可持续 | 云端服务可以替换，不让业务逻辑绑定某个平台 |

# 二、目标用户与使用场景

## 2.1 目标用户

第一阶段只服务两位真实用户：

- 用户 A：共同空间创建者。
- 用户 B：通过邀请加入共同空间。

两个人拥有各自独立的账号和身份，但共享同一个情侣空间。

不设置管理员和普通成员的等级差异。双方在共同空间中拥有对等的基本权限。

## 2.2 核心使用场景

### 场景一：每天打开应用

用户进入首页，可以看到：

- 两个人的头像和昵称。
- 相恋天数。
- 当前纪念日。
- 下一次见面倒计时。
- 今日问候。
- 最近新增的共同回忆。
- 对方最近参与互动的情况。

首页不应该像任务管理器一样塞满待办事项，而应该像一个可以随时打开的共同空间。

### 场景二：记录一段回忆

用户选择照片，填写标题、时间和描述。

保存后：

- 数据首先写入本地数据库。
- 图片先保存在本地。
- 网络可用时进入同步队列。
- 对方同步成功后可以查看。
- 对方可以在回忆下评论或表达回应。

### 场景三：每日双人问答

系统每天提供一道问题。

例如：

- 今天有什么瞬间让你开心？
- 如果明天可以见面，你最想做什么？
- 最近有没有什么事情想告诉我？

双方分别提交答案。

在双方都完成之前，任何一方都不能提前查看另一方的答案。

双方提交后，才允许揭晓。

### 场景四：给未来写一封信

用户写下一封信，设置解锁日期。

信件在解锁之前：

- 正文不下发给未授权用户。
- 不能通过修改手机时间提前解锁。
- 不能通过客户端接口绕过限制。

到达解锁时间后，由服务端验证并开放读取。

### 场景五：异地见面计划

两个人可以共同记录：

- 下一次见面日期。
- 见面地点。
- 交通和住宿计划。
- 想一起完成的事情。
- 见面倒计时。

# 四、核心功能详细规划

## 4.1 首页

### 功能目标

让用户打开应用后，第一时间感受到两个人共同生活的氛围。

### 页面结构

#### A. 双人关系卡片

展示：

- 双方头像。
- 双方昵称。
- 相恋日期。
- 已相恋天数。
- 一句关系状态文案。

相恋天数根据双方确认的恋爱开始日期计算。

不能简单将天数写死在数据库中，应根据日期动态计算。

#### B. 下一次见面

展示：

- 见面日期。
- 剩余天数。
- 见面地点。
- 简短备注。

没有设置时，显示轻量引导，不显示空白大卡片。

#### C. 今日问候

可以采用随机问候或每日轮换文案。

不需要接入付费 AI。

#### D. 最近回忆

展示最近新增的共同回忆。

点击进入回忆详情。

#### E. 快捷入口

保留：

- 写回忆。
- 写日记。
- 每日问答。
- 写一封信。

### 设计要求

首页应具有明确的视觉层级。

不使用过多卡片叠加，不将所有功能都放在首页。

---

## 4.2 回忆模块

回忆是整个产品最重要的长期内容模块之一。

### A. 共同时间线

按时间倒序展示共同回忆。

每条回忆包含：

- 标题。
- 图片。
- 内容。
- 发生时间。
- 创建人。
- 创建时间。
- 评论和回应。

支持按照年份、月份查看。

### B. 相册

支持：

- 多图上传。
- 图片预览。
- 图片删除。
- 图片说明。
- 按时间筛选。
- 按回忆分类。

图片需要支持本地保存和云端私有存储。

图片不能使用永久公开访问链接。

### C. 共同日记

共同日记是两个人都能查看和参与的内容。

支持：

- 新建。
- 编辑。
- 删除。
- 评论。
- 时间排序。

### D. 个人日记

个人日记是非常重要的隐私模块。

必须区分：

- PRIVATE：个人私密日记。
- SHARED：双方共同日记。

PRIVATE 默认只保存在本地。

PRIVATE 不允许进入 Outbox，不允许自动上传，不允许因为某次同步失败而被误传到云端。

如果以后确实需要个人日记云备份，必须作为独立功能设计，并由用户明确开启。

### E. 评论与回应

共同回忆允许另一方评论。

支持：

- 文字评论。
- 删除自己的评论。
- 评论时间。
- 评论所属回忆。

第一版不需要复杂表情互动系统。

## 4.3 互动模块

### A. 每日双人问答

这是互动模块的核心功能。

工作流程：

```text
系统生成当日问题
        ↓
双方分别提交答案
        ↓
服务端检查双方提交状态
        ↓
是否双方都已提交？
    ├── 否：继续隐藏双方答案
    └── 是：允许双方查看
        ↓
保存问答历史
```

必须由服务端保证揭晓条件。

客户端不能自行判断双方都提交后就直接读取对方答案。

### B. 悄悄话

允许用户给另一方发送一段短消息。

支持：

- 发送。
- 接收。
- 已读状态。
- 历史记录。
- 本地通知。

第一版不做完整即时通讯系统。

消息采用轻量同步方式，不接入需要额外付费的推送服务。

### C. 双人小游戏

后续逐步增加：

- 默契问答。
- 猜猜对方。
- 今日选择题。
- 共同挑战。
- 回忆猜图。

小游戏应以双方互动为主，不引入复杂排行榜和社交体系。

## 4.4 信箱模块

### A. 写给未来的信

支持：

- 写信。
- 设置收信人。
- 设置解锁时间。
- 添加封面。
- 查看信件状态。

状态：

- DRAFT：草稿。
- LOCKED：未解锁。
- UNLOCKED：已解锁。
- CANCELLED：已取消。

### B. 时间胶囊

允许用户写下一段内容，设置未来日期。

可以是：

- 写给未来的自己。
- 写给未来的对方。
- 写给未来的两个人。

### C. 服务端解锁机制

必须满足：

1. 服务端保存解锁时间。
2. 服务端使用可信时间判断。
3. 未解锁时不向客户端返回正文。
4. 客户端修改系统时间无效。
5. 服务端接口不允许绕过解锁条件。

# 六、UI 与视觉设计规范

## 6.1 设计定位

整体风格：

**温暖、简洁、轻盈、私密、有陪伴感。**

不做传统粉色情侣软件的刻板设计。

也不使用大量爱心、花朵、渐变和装饰图案。

视觉上应更接近成熟的现代移动应用。

## 6.2 视觉规范

### 色彩

建议建立统一颜色体系：

- 主背景：暖白色。
- 主文字：深灰色。
- 次级文字：中性灰。
- 主强调色：柔和的暖红或玫瑰色。
- 辅助色：低饱和度暖橙。
- 成功状态：低饱和度绿色。

深色模式作为后续功能。

### 圆角

统一使用设计 Token。

不要在每个页面单独设置圆角。

### 间距

建立统一的间距体系：

- 4dp：微小间距。
- 8dp：紧凑间距。
- 12dp：常规间距。
- 16dp：主要内容间距。
- 24dp：模块间距。
- 32dp：页面分区间距。

### 动效

优先使用：

- 页面淡入淡出。
- 卡片轻微位移。
- 图片渐进加载。
- 状态切换动画。
- 轻量点击反馈。

禁止为了视觉效果使用大量复杂动画。

## 6.3 交互原则

1. 常用功能尽量两步内完成。
2. 输入内容应自动保存草稿。
3. 失败时必须保留用户输入。
4. 网络异常不能导致内容丢失。
5. 删除操作必须有明确反馈。
6. 加载状态不能让页面长时间空白。
7. 空状态要有引导，但不能制造强制任务感。

# 八、本地数据与云端同步架构

## 8.1 本地优先原则

Room 是本地业务数据的主要读取来源。

任何新增内容：

1. 先写入 Room。
2. 立即更新 UI。
3. 根据数据类型决定是否需要同步。
4. 需要同步的数据进入 Outbox。
5. 网络可用时由统一同步系统上传。
6. 上传成功后更新同步状态。

不能因为云端请求失败而阻止用户保存回忆。

## 8.2 数据同步状态

统一使用：

- LOCAL_ONLY：仅本地。
- PENDING_UPLOAD：等待上传。
- SYNCED：同步完成。
- PENDING_DELETE：等待删除。
- CONFLICT：存在冲突。
- FAILED：同步失败。

## 8.3 Outbox 队列

建议字段：

```text
taskId
entityType
entityId
operation
payload
clientMutationId
createdAt
retryCount
syncStatus
lastError
```

要求：

- 每条操作拥有唯一 ID。
- 上传请求必须支持幂等。
- 重试不能造成重复创建。
- 删除操作必须能正确同步。
- 冲突不能静默覆盖。
- PRIVATE 日记永远不能进入 Outbox。

## 8.4 同步调度

由全 App 统一的 SyncCoordinator 负责。

不允许每个页面自行创建独立轮询任务。

同步触发时机：

- App 回到前台。
- 用户手动刷新。
- 网络恢复。
- 本地存在待上传任务。
- 定时后台任务执行。

建议初期采用自适应轮询：

- 首页：约 60 秒。
- 互动页面：约 20 秒。
- 后台：停止前台轮询。
- 网络恢复：立即尝试同步。
- 手动刷新：立即同步。

具体间隔应根据实际资源消耗和用户体验调整。

## 8.5 冲突处理

不能简单采用最后写入覆盖所有数据的方案。

建议：

- 普通回忆：保留版本信息，冲突时提示或合并非冲突字段。
- 评论：采用独立记录，避免整条覆盖。
- 日记：记录更新时间和版本号。
- 删除：采用明确删除状态。
- 双人问答：由服务端维护提交状态和揭晓状态。
- 未来信：由服务端维护锁定与解锁状态。

# 九、CloudBase 免费云端规划

## 9.1 当前预算政策

当前阶段必须保持 0 元。

允许：

- 使用 CloudBase 免费体验版。
- 验证 PostgreSQL。
- 验证身份认证。
- 验证 HTTP API。
- 验证私有存储。
- 验证云函数。
- 验证 RLS。
- 进行小规模测试。

禁止：

- 自动升级付费套餐。
- 开启超额按量付费。
- 自动续费。
- 购买资源包。
- 购买短信服务。
- 购买 CDN。
- 购买独立服务器。
- 购买域名。
- 未经授权创建任何收费资源。

未来是否付费，由用户主动决定。

不能将“未来可能付费”理解为“现在允许升级”。

## 9.2 免费体验版使用原则

CloudBase 免费体验版作为第一阶段云端验证方案。

必须先验证：

1. 免费环境创建资格。
2. PostgreSQL 实际可用性。
3. 数据库空闲期间的资源消耗。
4. 3000 资源点/月的实际消耗情况。
5. 云函数实际执行限制。
6. 私有存储是否可用。
7. API 请求资源点消耗。
8. 免费额度耗尽后的具体行为。
9. 环境到期后的数据导出能力。

免费体验版不等于永久免费，也不保证所有服务可以无限使用。

如果额度不足：

- 暂停云端上传。
- 保留本地记录。
- 显示同步暂停状态。
- 不自动升级。
- 不自动购买资源。
- 保证用户可以继续使用本地功能。

## 9.3 云端负责什么

云端仅负责必要的双人共享功能：

- 用户身份认证。
- 双人空间关系。
- 邀请码绑定。
- 共同回忆同步。
- 共同日记同步。
- 每日问答。
- 评论和悄悄话。
- 未来信解锁。
- 私有图片存储。

不把所有个人数据都上传云端。

## 9.4 服务端必须负责的业务

以下逻辑不能只放在客户端：

### 邀请码核销

- 验证邀请码。
- 验证有效期。
- 验证空间状态。
- 原子性绑定。
- 防止重复绑定。

### 每日问答

- 验证用户身份。
- 验证当日问题。
- 保存提交状态。
- 双方提交完成后开放揭晓。

### 未来信

- 使用服务端可信时间。
- 未解锁前不返回正文。
- 服务端检查授权。
- 防止客户端绕过时间限制。

### 图片访问

- 私有 Bucket。
- 不使用永久公开 URL。
- 服务端验证用户和空间权限。
- 签发短时效访问链接。

### 空间解散

- 验证双方身份。
- 执行空间状态变更。
- 保护历史数据。
- 不能因为一方退出就直接删除另一方的数据。

## 9.5 数据安全规则

必须使用：

- JWT 身份认证。
- 服务端身份验证。
- PostgreSQL GRANT。
- RLS 行级安全策略。
- 必要的云函数权限校验。

严禁信任客户端自行传入的 userId 或 coupleId。

用户身份必须来自经过验证的认证上下文。

数据库默认拒绝未授权访问。

# 十一、隐私与安全设计

## 11.1 隐私分级

建议分为三类：

### PRIVATE

仅本人可以访问。

默认仅本地保存。

### SHARED

双方可以访问。

允许云端同步。

### SERVER_CONTROLLED

必须由服务端执行权限判断。

例如：

- 每日问答揭晓。
- 未来信解锁。
- 邀请码核销。
- 空间解散。

## 11.2 账号与空间安全

必须支持：

- 登录身份验证。
- 双人绑定校验。
- 空间成员权限检查。
- 非成员禁止读取共同数据。
- 退出登录后清理认证凭据。
- 账号和空间状态异常时安全降级。

## 11.3 数据导出

必须预留数据导出能力。

建议支持：

- 回忆文本导出。
- 日记文本导出。
- 图片原图导出。
- 纪念日导出。
- 问答历史导出。

导出操作不能依赖云端一直可用。

## 11.4 空间解散

空间解散需要独立状态机。

不能简单删除数据库记录。

需要明确：

- 谁发起解散。
- 双方是否确认。
- 共同数据如何处理。
- 个人数据如何保留。
- 本地数据是否保留。
- 云端访问权限如何撤销。

# 十八、项目最终目标

「予你 · Us」最终不应该只是一个记录恋爱天数的软件。

它应该是一处属于两个人的数字空间。

今天可以记录一顿饭、一张照片、一段聊天后的心情。

明天可以写下下一次见面的期待。

一年以后，可以回头看看两个人一起经历了什么。

更久以后，即使生活节奏发生变化，这些记录仍然能够被保存、查看和回忆。

**产品的核心不是让两个人每天都必须打开它，而是当其中一个人想起另一个人时，这里始终有一个属于两个人的位置。**
